# Phase 1-2 — 부동소수점(Floating Point) & 문자 인코딩(Character Encoding)

---

> **목표**: 정수 다음으로
> (1) 소수를 컴퓨터가 어떻게 근사하는지(왜 `0.1 + 0.2 ≠ 0.3`인지),
> (2) 문자를 어떻게 숫자로 바꾸는지(UTF-8, 그리고 한국어 LLM 토큰이 왜 비싼지)를 이해한다.

## 1. 개념 및 정의

### Part A. 부동소수점

#### 1-1. 왜 소수가 어려운가

정수는 깔끔하지만, 소수는 비트로 표현할 때 **유한한 비트로 무한히 많은 실수를 근사**해야 함.
핵심 문제 : 10진수로는 깔끔한 `0.1`이 **2진수로는 무한 반복 소수**

```
0.1₁₀ = 0.0001100110011001100110011...₂  (0011 무한 반복)
```

10진수에서 `1/3 = 0.333...`이 끝나지 않듯, 2진수에서 `0.1`이 끝나지 않는다. 컴퓨터는 어딘가에서 잘라야 하고, 그래서 **미세한 오차**가 생긴다.


#### 1-2. IEEE 754 표준

현대 컴퓨터의 소수 표현 표준. 과학적 표기법(`±유효숫자 × 밑^지수`)의 2진 버전이다.

```
값 = (-1)^부호 × 1.가수부 × 2^(지수부 - 바이어스)
```

| 구성요소 | 32비트(float/single) | 64비트(double, Python float) |
|---|---|---|
| 부호 (sign) | 1비트 | 1비트 |
| 지수 (exponent) | 8비트 | 11비트 |
| 가수 (mantissa/fraction) | 23비트 | 52비트 |
| 유효 자릿수(10진) | 약 7자리 | 약 15~16자리 |
 

> "부동(floating)"의 의미
> 소수점의 위치가 지수에 따라 **떠다닌다(고정 아님)**
> 그래서 아주 큰 수와 아주 작은 수를 같은 형식으로 표현할 수 있다.


#### 1-3. 핵심 결론 3가지

1. **`==`로 소수를 직접 비교하지 마라.** `0.1 + 0.2 == 0.3`은 `False`.
2. **돈/정밀 계산엔 부동소수점을 쓰지 마라.** `Decimal`이나 정수(센트 단위)를 써라.
3. **특수값이 있다**: `inf`(무한대), `-inf`, `nan`(Not a Number). `nan`은 자기 자신과도 같지 않다(`nan != nan`).

### Part B. 문자 인코딩
 
#### 1.4 문자 → 숫자: 코드포인트와 인코딩

컴퓨터는 숫자만 안다. 그래서 문자마다 번호를 매겨야 한다.
 
| 용어 | 정의 | 예 |
|---|---|---|
| **문자집합(charset)** | 문자 ↔ 번호(코드포인트)의 대응표 | Unicode |
| **코드포인트** | 한 문자에 할당된 고유 번호 | `'A'` = U+0041, `'가'` = U+AC00 |
| **인코딩(encoding)** | 코드포인트를 실제 바이트로 바꾸는 규칙 | UTF-8, UTF-16 |


#### 1.5 ASCII → Unicode → UTF-8의 역사
 
| 인코딩 | 표현 범위 | 한 문자 크기 | 한계/특징 |
|---|---|---|---|
| **ASCII** | 영어·숫자·기호 128개 | 1바이트(7비트) | 한글·한자 표현 불가 |
| **Unicode** | 전 세계 모든 문자(코드포인트 정의) | (추상적 번호) | "번호표"일 뿐, 저장 방식은 인코딩이 결정 |
| **UTF-8** | 유니코드 전체 | **가변 1~4바이트** | ASCII 호환, 웹 표준, 영어는 1바이트로 효율적 |
| **UTF-16** | 유니코드 전체 | 2 또는 4바이트 | 영어도 2바이트, 일부 환경에서 사용 |


#### 1.6 UTF-8의 가변 길이 — 한국어 비용의 뿌리
 
UTF-8은 문자에 따라 바이트 수가 다르다:
 
| 문자 종류 | UTF-8 바이트 수 | 예 |
|---|---|---|
| 영어·숫자·기본 기호 (ASCII) | **1바이트** | `A` → `41` |
| 라틴 확장, 그리스어 등 | 2바이트 | `é` → `C3 A9` |
| **한글·한자·일본어** | **3바이트** | `가` → `EA B0 80` |
| 이모지 등 | 4바이트 | `😀` → `F0 9F 98 80` |
 
> **"한국어 토큰 2~3배 비용"의 정체**
> LLM은 텍스트를 토큰으로 쪼개는데, 토크나이저가 대개 UTF-8 바이트나 서브워드 기반이다.
> 실제 이유는 **"토크나이저가 한글을 영어보다 덜 효율적으로 압축함."**
> 이게 입력·출력 토큰 비용 증가로 직결된다. (정확한 비율은 모델 토크나이저에 따라 다르지만, "한글 = 영어보다 바이트가 많다"가 근본 원인.)
 
 > 왜 이런 현상이 발생할까?
 > 영어는 단어 경계(공백)가 명확하고 자주 쓰이는 단어가 반복되어 토큰 하나에 담기 쉬움
 > 한국어는 조사와 머이가 다양하게 붙어 형태가 많이 변하기 때문
 > 많은 토크나이저는 영어 중심의 대규모 데이터로 학습되어 영어 표현을 더 효율적으로 압축함.
